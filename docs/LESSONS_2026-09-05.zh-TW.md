## 1. 驗證器從報告的最後一列取任務完成時間（值 22.2266 分）

我們提交的軌跡在 5982.99 s 進入 5 km。腳本依當時的政策跑滿 $4T_A$。

主辦回傳三個數字：**C = 23815.43、D = 2.394、E = 6.996，總分 73.0203。**

- **D = 2.394 是他們自己算出的最小距離**，與我方報告最小的那一列（t = 5982.992523 s、
  Δr = 2.394038 km，前後列 6.878 / 11.666 km）吻合到小數第三位。他們**看到了**攔截。
- **C = 23815.43 = $4T_A$**，等同判定「從未攔截」，時間項因此為 0。
- 唯一能對上總分的組合是 $50 + 0 + 23.0203 = 73.0203$。

**結論：驗證器的完成時間取自報告最後一列，最小距離取自全部列。**

規則 §4 寫 $T_{team} = \min(t_{int}, 4T_A)$，兩種讀法在條文上都成立 —— 這正是不能只讀條文的理由。
§8 寫明「所有結果以主辦單位驗證程式為準」。

依 §4 應得：$50 + 22.2266 + 23.0203 = 95.2470$。

### 修正與其陷阱

`policy.mission_end_policy` 預設 `"interception"`：成功候選的 Mission Sequence
**結束在首次落入球內的那一列上**。失敗候選仍跑滿 $4T_A$（那時 $T_{team}=4T_A$、
距離項是 $\Delta r(4T_A)$，最多 50 分）。後來停止點再往內移：停在 GMAT 量到首次深入球內
`policy.stop_depth_km`（預設 1.5 km）的那一刻。

**尾段長度不能猜，必須算。** GMAT 從**最後一次機動**起每 `Propagator.MaxStep` 秒寫一列，
相位與我們分析的 $t_{int}$ 無關：

$$t_{\text{entry row}} = t_{\text{last burn}} + \left\lceil \frac{t_{int} - t_{\text{last burn}}}{\text{step}} \right\rceil \times \text{step}$$

實測 6 脈衝候選：$t_{int}$ = 5676.2438、最後機動 2556.7897、step = 1 s，
進入列落在 **5676.7897（晚 0.546 s）**。這條軌跡以 12.6 km/s 掠過，球內**只有一列**。

| 尾段策略 | 最後一列 | Δr | 驗證器讀到 |
|---|---|---:|---:|
| 固定 1.0 s | 進入列後 0.45 s | 7.57 km（球外） | 98.3151 |
| 固定 2.0 s | 進入列後 1.45 s | 20.13 km（球外） | 98.3117 |
| **對齊到進入列** | **就是進入列** | **1.86 km** | **98.3167** |

對齊後兩種讀法給出相同分數。這個 bug 是 `scripts/check_report_rows.py`
在它自己作者的修正上抓到的。

## 2. 計分單位由主辦的評分本身確定

規則沒印輸入單位。主辦回傳 E = 6.996 與總分 73.0203：

$$\frac{25}{1+e^{1.1862(6.996-9.0643)}} = 23.0203, \qquad 50 + 0 + 23.0203 = 73.0203$$

若 $C_v$ 讀 m/s，指數溢位、該項為 0、總分會是 50.0000。
**ΔV 用 km/s，時間用 s。** $C_t$ = 6505.65 落在 23815 s 視窗內，且 C 回傳 23815.43 未經換算，
也印證時間是秒。

## 3. 公告係數會反轉「省 ΔV」的預設

本場係數下：時間項在 6505 s 是懸崖、到 7500 s 只剩 0.47 分；ΔV 項到 6 km/s 仍有 24 分。
**脈衝幾乎免費，時間是一切。**

這與搜尋層「最省 ΔV、一到兩次脈衝」的內建預設完全相反：

| | 攔截 | 總 ΔV | 分數 |
|---|---:|---:|---:|
| 內建搜尋最佳 | 21558 s | 1.557 km/s | 74.997 |
| 放開脈衝數與間隔 | 5676 s | 6.184 km/s | **98.319** |

### 有效的搜尋順序

1. 算 $\partial S/\partial t_{int}$ 與 $\partial S/\partial \Delta V$，知道哪一項是槓桿。
2. `scripts/safe_delta_v_floor.py` 掃「地球安全的單脈衝 ΔV」對到達時刻的地形。
   **那一欄是上界不是下限**：該表在 5700 s 要 8.34 km/s，實飛的五脈衝解在 5675 s
   只花 6.19 km/s，便宜 2.15 km/s。表的用途是找可達區間與編列脈衝數，不是當答案。
3. 把超過上限的單脈衝拆成 N 次：前 N−1 次沿同方向打滿，第 N 次由 Lambert 補完。
   這正是主辦範例解答的結構（1.5 + 0.741 km/s）。
4. **自由間隔精修**。脈衝間隔不要鎖死在最小值：放開後多 3 分，最佳結構是
   「起燃 → 滑行 2264 s → 連發」，不是等間隔連發。
5. 每個約束用**硬牆**而非罰項。實測一個帶軟罰的精修交出 `|dv| = 1495.098 m/s`（超標）
   與剛好貼在高度底線的解。

## 4. 中心天體檢查必須涵蓋整段弧

點質量重力沒有地表，積分器會很樂意把太空船算穿地心並在另一側回報攔截。

- 所有便宜的 Lambert 弧都在攔截前或攔截後鑽進地球。單脈衝極小值在 3575 s（近地點 3931 km）、
  6505 s（4198 km）、9444 s（5475 km）**全部在攔截前就進入地下**。
- 只約束攔截前，優化器會用俯衝換速度：一個 95.25 分的解在攔截後 100 秒撞地。
- `constraints.flies_through_central_body` 只看到攔截為止 —— 它是提交前的閘門，不是搜尋的約束。
  搜尋要自己帶約束，`scripts/audit_burn_table.py --require-safe-through-horizon` 可事後查核。
  （力模型不是二體時，audit 一律判到 $T_{max}$，攔截則交給 GMAT 報告。）

在「整段 $4T_A$ 不入地」的嚴格要求下，最佳是 7 脈衝、9.700 km/s、攔截 4671.5 s、**82.98 分**。

## 5. 不要為第三位小數削安全邊際

把每次脈衝從 1495 推到 1499.999 m/s、間隔從 101 推到 100.0001 s：

| | 分數 | 最近距離 | 違規餘裕 |
|---|---:|---:|---|
| 貼邊界 | 98.3202 | 4.15 **km** | 1 m/s / 0.1 ms |
| 守邊際 | 98.3185 | 4.15 **m** | 5 m/s / 1 s |

換到 0.0016 分，代價是餘裕縮 5 倍，而每次違規機動扣 10 分、驗證器的浮點容差未公告。
§6 同分判定第一順位正是最小相對距離 —— 守邊際那版在總分幾乎相同時**同分判定完勝**。

## 6. 本場達到的與可證明的上界

純計分的鬆弛上界：

$$S \le 50 + \frac{25}{1+e^{-k_t C_t}} + \frac{25}{1+e^{-k_v C_v}} = 99.9994650$$

取 $t=0$ 與 $\Delta V=0$ —— **物理不可達**，兩船初始相距 12842 km 而瞬時脈衝不改變位置。

實際達到並經真實 GMAT R2026a 重播確認：**98.3185410**
（6 脈衝、總 ΔV 6.184 km/s、攔截 5676.24 s、最近距離 **4.15 公尺**、攔截前高度 422 km）。
66 個作業涵蓋 5/6/7 脈衝、37 個起點全部收斂到同一族；7 脈衝沒有優勢，因為 ΔV 項在
6 km/s 附近已近飽和。與上界的 1.68 分差距來自 84.31° 平面夾角的幾何本身，不是搜尋不足。

## 7. 開放式模板

本場 Mission Sequence 只有一行 Propagate，沒有任何 `ImpulsiveBurn` 或 `Maneuver`。
規則要求 B「可進行多次瞬時脈衝機動」，模板卻沒有提供表達方式 ——
**新增資源與指令是題目要求的動作，不是違規改動**。

- `script_renderer._render_open_template` 走這條路，`tests/unit/test_open_template.py` 涵蓋。
- `pursuer_name` 在此為必填：沒有 `Maneuver` 指令，parser 無從得知哪一艘是我方，
  會 fail closed。`target_name` 可省略，parser 取另一艘。
- `ReportFile1.Filename` 內的隊號佔位符必須換成實際隊號 —— 那是主辦要求。

## 8. stock GmatConsole 不吃含 OpenFrames 的 script

主辦 script 含 `OpenFramesInterface` / `OpenFramesView` / `GroundTrack`。
console 模式硬編碼跳過 GUI plugin（字串就在 `libGmatBase.so`），整份 script 被拒 ——
實測 58 個錯誤、exit 1。

- `orbitwin solve --gmat-verify-top N` **不受影響**：診斷副本會註解掉繪圖物件。
- `orbitwin baseline` 與 `certify` 的 exact 重播**會失敗**。2026-11-06 起（簽核見
  `docs/COMPETITION_POLICY.md`），`gmat.console_copy` 開著時（排位賽設定檔開啟），它們改飛
  只拿掉繪圖行、並逐行對照提交 script 證明過的副本（`docs/RUNBOOK.md` 第 6c 步）。
- 沒有那份副本時，正式報告只能用 GMAT **GUI** 產生（`docs/RUNBOOK.md` 第 6b 步），
  再照 RUNBOOK 第 7 步跑 `check_report_rows`。
- 錯誤訊息只讀 GMAT 自己的錯誤：`**** ERROR ****` 紀錄，和它不加這個標記就印出的
  `... Exception:`，每筆只引一次並附上 GMAT 印的那一行。算不算在 OpenFrames 物件頭上，
  看 GMAT 印的那一行是不是 script 建立的 OpenFrames 物件的 Create 或欄位；沒有那一行
  才看 R2026a 的措辭。
  不是那些 OpenFrames 物件的錯誤會先引出來（`GMAT reported: ...`），這時不叫人去 GUI：
  GUI 用同一個 interpreter，也會拒絕，而官方 script 不能改，所以停下來交給主辦
  （RUNBOOK 的 Stop rules）。錯誤多到沒讀完（超過 10 000 筆不同的）也不叫人去 GUI。
  GroundTrack 只在實測的情形下被點名：沒寫出的報告是 script 會寫的（WriteReport 不是
  false），且 GroundTrack 建在那個 ReportFile 之前。timeout 或檔案大小上限不算在繪圖物件頭上。
